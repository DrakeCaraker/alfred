# Telemetry Policy: What to Extract and How to Use It

Last updated: 2026-03-29

## Data Sources

Alfred has two data pipelines:

1. **Session telemetry** — per-user JSON files in `.pilot/telemetry/`. Written directly by the Stop hook (shell-level, no Claude compliance needed). Contains demographics, session counts, duration, branch type, feedback count.

2. **Collective signals** — encrypted, anonymized correction patterns in `DrakeCaraker/alfred-collective`. Generated by `/self-improve` from feedback memories. Contains corrections, rules, graduations, automations, gaps.

## Field Reliability

### Tier 1: Reliable (shell-computed)

| Field | What it tells you | Action it drives |
|-------|-------------------|-----------------|
| `persona` | Which roles adopt Alfred | Invest in popular personas, investigate low adoption |
| `coding_level` | Skill level of user base | Tune explanation depth |
| `sessions[]` length | Retention / stickiness | If users stop at session 2, onboarding is broken |
| `duration_bucket` | Engagement depth | If all "short," Alfred isn't used for real work |
| `days_active` | Return rate | 1 day = tried and quit. 10+ = retained |
| `branch_type` | Branching discipline | If 80% on main, `/new-work` suggestion isn't working |
| `feedback_memory_count` | Are corrections captured | 0 across many sessions = Rule #4 is broken |
| `bookmark_saved` | Session continuity | false = session-end behavior not firing |

### Tier 2: Partially reliable (Claude-reported)

| Field | What it tells you | Caveat |
|-------|-------------------|--------|
| `commands_used` | Feature popularity | **Always empty in current data.** Claude-reported from memory. Don't rely on for decisions. |
| `patterns_state` | Teaching effectiveness | Claude must read onboarding-state.json and report. Not populated by shell hook. |
| `graduated_this_session` | Learning progress | Claude-reported. Use collective graduation signals instead for cross-user analysis. |
| `custom_role_category` | Persona gap detection | 3+ users in same category = build new persona |
| `persona_fit` | Persona quality | High false rate = persona needs rework |

### Tier 3: Collective signals (encrypted, requires admin ingest)

| Signal type | What it tells you | Action it drives |
|-------------|-------------------|-----------------|
| `correction` | What stock personas are missing | 3+ occurrences → add guardrail to persona |
| `rule` (is_custom=true) | What users add that Alfred doesn't ship | Gap in stock persona → add to template |
| `gap` | Explicit persona holes | Direct feedback on what's missing |
| `graduation` | Cross-user learning curves | Habit X takes 10 sessions everywhere → lesson is bad |
| `automation` | What users automate | Popular automations → ship as default hooks |

## Usage by Phase

### Phase 2-3: 1-10 users

- Read individual telemetry files directly — don't aggregate (N too small)
- Key questions:
  - Did they return after session 1?
  - Did any habit graduate?
  - What persona did they pick?
- If ALL users pick ml-ds → other personas poorly positioned
- If NO habits graduate → teaching engine is broken
- Collective signals: read individually, look for unexpected corrections

### Phase 4: 10-50 users

- Run `scripts/aggregate-pilot.sh` — distributions become meaningful
- Key questions:
  - Session 1→3 retention rate?
  - Which habits graduate fastest/slowest?
  - Do custom_role users cluster in one category?
- If 3+ users cluster in custom_role_category → build that persona
- If a habit never graduates → rewrite its lesson
- Collective signals: look for 3+ occurrence patterns → promote to stock personas

### Scale: 50+ users

- Patterns are statistically meaningful
- Build retention funnel: install → session 1 → session 5 → first graduation
- Compare graduation rates across personas and coding levels
- Collective signals become the primary improvement driver

## Admin Workflow

```bash
# 1. Aggregate telemetry (when telemetry files are submitted)
bash scripts/aggregate-pilot.sh

# 2. Ingest collective signals
export ALFRED_COLLECTIVE_KEY='<key>'
bash scripts/collective-sync.sh ingest

# 3. Review recommended patterns (3+ occurrences)
# → Add to stock personas as guardrails
# → Commit and push to Alfred repo

# 4. Check persona convergence
# → 3+ users in same custom_role_category = build new persona
```

## Known Limitations

1. **commands_used is dead data.** The hook writes `[]` by default. Claude rarely populates it. Don't use for feature prioritization until a reliable capture mechanism exists.

2. **patterns_state depends on Claude compliance.** The telemetry hook should be updated to read `onboarding-state.json` directly in shell (like it reads persona/coding_level) instead of relying on Claude.

3. **Collective signals require the longest dependency chain.** Rule #4 compliance → feedback memories → /self-improve → signal generation. Each step has a compliance gap.

4. **No churn detection in aggregator.** A `last_seen` metric per user (derivable from `max(date)`) would flag drop-offs. Not yet implemented.

5. **No retention funnel in aggregator.** Count of users at session 1, 3, 5, 10 would be the highest-value improvement.

## Go/No-Go Metrics

| Metric | Target | Source | Reliable? |
|--------|--------|--------|-----------|
| Installs (month 1) | 50+ | GitHub stats + telemetry file count | Yes |
| Bootstrap completions | 30+ | Telemetry files with session_number=1 | Yes |
| Session retention (5+ sessions) | 30%+ | sessions[] length per user | Yes |
| Avg habits graduated | 3+ | Collective graduation signals | Partially |
| Corrections submitted | 100+ | Collective signal count | Partially |
| Persona most popular | — | persona field distribution | Yes |

## Policy: Don't Decide Based On

- commands_used (always empty)
- patterns_state from telemetry (Claude-reported, unreliable)
- Any metric with N < 10 users (noise, not signal)
- Absence of collective signals (dependency chain may be broken, not proof users have no corrections)
